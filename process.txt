NGINX2ROOT
Guía de inventario, detección, mitigación,
actualización y verificación
NGINX instalado directamente en un servidor Linux (sin Docker)

Campo	Detalle
Fecha de elaboración	18 de noviembre de 2026
Alcance	NGINX Open Source / NGINX Plus instalado en el sistema operativo anfitrión
Distribución de referencia	Ubuntu/Debian. En RHEL, AlmaLinux, Rocky Linux y otras, seguir el gestor y aviso de seguridad propios.
Objetivo	Identificar instancias y configuraciones expuestas, aplicar el parche del proveedor y documentar evidencias.

IMPORTANTE: esta guía es defensiva. No incluye pruebas de explotación.

 1. Resumen ejecutivo
NGINX2Root es el nombre usado por el equipo investigador Xint para agrupar cinco vulnerabilidades críticas de NGINX y una vulnerabilidad separada del kernel Linux que, según la investigación, podría encadenarse con fallos de NGINX para elevar privilegios hasta root. El nombre NGINX2Root no es el nombre oficial de un producto ni de una única CVE.
Las vulnerabilidades de NGINX pueden permitir que un atacante remoto no autenticado provoque la caída de procesos worker y, bajo condiciones específicas, ejecute código con los privilegios del worker. La elevación posterior a root depende de la vulnerabilidad independiente del kernel y de las condiciones del sistema; no debe asumirse que cualquier NGINX vulnerable equivale automáticamente a acceso root.
Prioridad: inventariar primero todos los servidores accesibles desde Internet, comprobar qué funciones están activas y actualizar desde el canal oficial del sistema operativo o del proveedor de NGINX. Deshabilitar HTTP/2 puede reducir temporalmente la exposición a dos CVE, pero no sustituye el parche.
2. Vulnerabilidades incluidas
CVE	Área / condición relevante	Qué revisar
CVE-2026-123007	Módulo HTTP/2; HTTP/2 habilitado en un listener.	Listeners TLS que negocian h2.
CVE-2026-123633	HTTP/2 en escenarios con conexiones a upstream.	HTTP/2 y directivas como proxy_pass, fastcgi_pass o grpc_pass.
CVE-2026-123634	Resolver/proxy con combinación específica de variables y subsolicitudes mirror o SSI.	resolver, proxy_pass con variables, mirror, mirror_request_body, SSI.
CVE-2026-121810	HTTP/3 / QUIC; escenario de proxy upstream.	Listeners quic/http3 y directivas upstream.
CVE-2026-113425	Módulo de proxy de correo.	Configuración mail y proxy on.

La presencia aislada de una directiva no demuestra explotabilidad. Deben evaluarse versión/build, módulos compilados, contexto de configuración y condiciones exactas descritas por el proveedor.
3. Versiones: cómo interpretarlas correctamente
Para NGINX Open Source, los avisos publicados indican como versiones corregidas 1.30.7 (rama estable) y 1.31.9 (rama mainline). En términos generales, la rama estable 1.30.0–1.30.6 y la rama mainline 1.31.0–1.31.8 están afectadas, además de versiones anteriores desde que se introdujeron las funciones afectadas. La aplicabilidad exacta depende de cada CVE.
NGINX Plus tiene builds corregidos propios. No uses los números de Open Source para decidir si NGINX Plus está parcheado.
Distribuciones Linux pueden aplicar backports: el paquete puede conservar un número upstream aparentemente antiguo y aun así contener la corrección. Por eso, en Ubuntu/Debian hay que verificar la versión del paquete y el aviso de seguridad de la distribución; no basta con nginx -v.

5. Preparación y precauciones
•	Ejecuta el diagnóstico con una cuenta autorizada y privilegios sudo cuando sean necesarios.
•	Programa la actualización en una ventana de mantenimiento si el servidor presta servicios críticos.
•	Asegura acceso SSH alternativo o consola de recuperación antes de reiniciar servicios.
•	No pegues ni envíes la salida completa de nginx -T: puede revelar dominios internos, rutas, tokens, cabeceras y otros datos sensibles.
•	Registra fecha, hostname, responsable, IP/segmento, servicios afectados y resultado de cada comando.
•	Si el servidor usa Plesk, cPanel, un appliance o paquetes de un tercero, utiliza el procedimiento de ese fabricante; no mezcles paquetes manuales con los del panel.
6. Detección paso a paso (Ubuntu/Debian)
6.1 Identificar sistema operativo y servidor
hostnamectl
cat /etc/os-release
uname -r
systemctl status nginx --no-pager
Si el servicio no se llama nginx o no aparece, no concluyas que no existe. Puede ejecutarse con otro nombre, desde una instalación compilada manualmente o bajo un panel de hosting.
6.2 Identificar versión y procedencia del paquete
nginx -v 2>&1
nginx -V 2>&1
dpkg -l | grep -E 'nginx|openresty'
apt-cache policy nginx
Guarda la salida. nginx -V permite revisar argumentos de compilación y módulos; dpkg/apt muestran la versión empaquetada y el origen. Si fue compilado manualmente, revisa también la ruta del ejecutable y su método de actualización.
6.3 Localizar binario y proceso en ejecución
command -v nginx
readlink -f "$(command -v nginx)"
ps -eo user,pid,ppid,lstart,args | grep '[n]ginx'
systemctl show nginx -p ExecStart -p MainPID
Esto ayuda a detectar instalaciones múltiples o procesos que continúan usando un binario anterior. El proceso maestro y los workers deben corresponder a la instalación que estás actualizando.
6.4 Revisar directivas relevantes sin divulgar toda la configuración
sudo nginx -T 2>&1 | grep -nEi 'listen|http2|http3|quic|resolver|proxy_pass|fastcgi_pass|grpc_pass|mirror|ssi|mail|proxy on'
Este filtro es orientativo y puede omitir configuraciones construidas mediante includes o variables. La salida puede contener nombres de host internos; trátala como información confidencial.
CVE	Indicadores a revisar	Interpretación inicial
123007	http2 on; o listen ... http2; y listener público TLS.	HTTP/2 activo requiere evaluación prioritaria.
123633	HTTP/2 más proxy_pass / fastcgi_pass / grpc_pass.	Revisar escenario upstream específico.
123634	resolver; proxy_pass con variables; mirror / SSI y condiciones asociadas.	Requiere validar la combinación exacta.
121810	http3 on; o listen ... quic; y upstream.	HTTP/3/QUIC activo requiere evaluación.
113425	Bloques mail { ... } y proxy on;.	Revisar si se usa NGINX como proxy de correo.

6.5 Comprobar HTTP/2 negociado desde un equipo de prueba autorizado
openssl s_client -connect DOMINIO:443 -servername DOMINIO -alpn h2,http/1.1 </dev/null 2>&1
Sustituye DOMINIO por un host propio. Si aparece 'ALPN protocol: h2', el extremo TLS probado negocia HTTP/2. Si aparece http/1.1, negocia HTTP/1.1 en esa conexión. La ausencia de h2 no demuestra por sí sola que el servidor esté parcheado: verifica que TLS conectó correctamente y prueba cada listener/dominio relevante.
6.6 Comprobar exposición de red
sudo ss -lntup
Relaciona puertos escuchando (por ejemplo 80/443) con firewall, balanceador, NAT y reglas del proveedor cloud. Que un puerto escuche localmente no significa que sea accesible desde Internet; valida el camino de red con el equipo responsable.

8. Cómo actualizar de forma segura
8.1 Antes del cambio
sudo nginx -t
sudo cp -a /etc/nginx "/etc/nginx.backup-$(date +%F-%H%M)"
sudo apt update
apt-cache policy nginx
La copia de /etc/nginx no incluye necesariamente certificados, claves, archivos fuera de esa ruta ni configuraciones de aplicaciones. Asegura el backup conforme al procedimiento de tu organización. Protege especialmente las claves privadas.
8.2 Verificar que el repositorio ofrece una corrección
Consulta el aviso de seguridad de Ubuntu/Debian para la versión exacta del sistema y el paquete instalado. Confirma que la versión candidata incluye el parche de los CVE. Si no hay una versión corregida disponible, no fuerces una mezcla de repositorios ni instales un binario aleatorio: aplica la mitigación temporal aprobada y escala al proveedor.
apt-cache policy nginx
apt list --upgradable 2>/dev/null | grep -i nginx
8.3 Aplicar actualización
sudo apt upgrade
Revisa la lista de paquetes y confirma el cambio según el proceso de mantenimiento. Si la actualización afecta dependencias o servicios adicionales, revisa el impacto antes de continuar.
8.4 Validar configuración y reiniciar
sudo nginx -t
sudo systemctl restart nginx
sudo systemctl status nginx --no-pager
Se recomienda reiniciar el servicio después de actualizar para garantizar que los nuevos procesos carguen el binario corregido. Un reload por sí solo puede dejar procesos antiguos en ejecución, según el escenario. Verifica el proceso maestro y sus workers después del reinicio.
8.5 Confirmar versión y binario activo
nginx -v 2>&1
ps -eo user,pid,ppid,lstart,args | grep '[n]ginx'
systemctl show nginx -p MainPID -p ExecStart
Registra la versión del paquete y la evidencia del aviso de distribución que confirma el backport. En sistemas con paquetes de terceros, confirma el parche con ese proveedor.
9. Mitigación temporal si no puedes parchear inmediatamente
La mitigación temporal más citada para los dos fallos HTTP/2 consiste en deshabilitar HTTP/2 en los listeners afectados. Esto puede reducir la exposición a CVE-2026-123007 y CVE-2026-123633, pero NO corrige CVE-2026-123634, CVE-2026-121810, CVE-2026-113425 ni la vulnerabilidad separada del kernel.
Antes de cambiarlo, revisa cómo está configurado HTTP/2 en tu versión de NGINX. En configuraciones antiguas puede aparecer como parámetro en listen; en otras versiones se usa la directiva http2. Modifica el archivo de origen correcto, no solo un archivo generado por un panel. Prueba y programa el cambio:
sudo nginx -t
sudo systemctl restart nginx
Después comprueba la negociación ALPN con openssl s_client. Conserva HTTP/1.1 si la aplicación lo admite. Esta medida es temporal: restaura HTTP/2 únicamente después de confirmar que el parche está instalado.
Si se usa HTTP/3, mail proxy o la combinación específica de resolver/proxy/mirror/SSI, se necesita revisar y mitigar cada función de acuerdo con el aviso del proveedor. No elimines directivas a ciegas: puedes interrumpir aplicaciones.
10. Revisión posterior y señales de posible incidente
Una configuración vulnerable no demuestra que haya ocurrido una intrusión. Los siguientes controles ayudan a detectar anomalías, pero no son prueba concluyente ni sustituyen un análisis forense.
sudo journalctl -u nginx --since '24 hours ago' --no-pager
sudo grep -iE 'worker process|signal 11|segmentation fault|exited on signal' /var/log/nginx/error.log 2>/dev/null
ps -eo user,pid,ppid,lstart,args --forest
sudo ss -tunap
•	Investiga reinicios o caídas inesperadas de workers, especialmente si coinciden con tráfico anómalo.
•	Revisa procesos hijos inesperados, conexiones salientes no habituales y cambios recientes en cuentas, claves SSH, tareas programadas y archivos de configuración.
•	Centraliza logs y conserva evidencias antes de borrar archivos o reiniciar repetidamente.
•	Si existe indicio razonable de compromiso, activa respuesta a incidentes: aísla el servidor de forma controlada, preserva evidencias, rota secretos desde un entorno limpio y evalúa reconstruir desde una imagen confiable.
11. Kernel Linux: punto separado
La investigación NGINX2Root describe además una vulnerabilidad local del kernel Linux relacionada con SCTP que podría encadenarse para elevar privilegios. Es independiente de los cinco CVE de NGINX. No se debe asumir que actualizar NGINX la corrige.
Registra la versión del kernel (uname -r), consulta el aviso de seguridad de tu distribución y aplica las actualizaciones de kernel aprobadas. Si el proveedor aún no publica una corrección, sigue su guía oficial de mitigación; no desactives protocolos o módulos del kernel sin evaluar dependencias.

13. Criterios de resultado
Estado	Criterio
Corregido	El proveedor confirma el parche en el paquete/build instalado; NGINX se reinició; configuración y servicio validados.
Mitigado temporalmente	Se deshabilitó una función afectada para reducir riesgo, pero falta instalar el parche completo.
Expuesto	Versión/build sin corrección y condición vulnerable activa o no descartada.
Pendiente de validar	Faltan datos de paquete, configuración, proveedor o exposición de red.
No aplica	La instancia no usa el componente/función afectada y la evaluación documentada descarta esa ruta; mantener inventario.
